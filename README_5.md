# Web Labs --- Лабораторная работа №5

## Кеширование данных и управление сессиями с использованием Redis

### Описание

В рамках данной лабораторной работы в существующее Django-приложение
было добавлено кеширование данных с использованием Redis, а также
реализовано управление сессиями через хранение идентификаторов
access-токенов (JTI).

Основная цель --- снизить нагрузку на базу данных, ускорить обработку
запросов и обеспечить возможность мгновенного отзыва access-токенов.

------------------------------------------------------------------------

### Используемые технологии

-   Python 3.12
-   Django
-   PostgreSQL
-   Redis
-   Docker / Docker Compose

------------------------------------------------------------------------

### Запуск проекта

1.  Убедитесь, что установлен Docker и Docker Compose
2.  В корне проекта создайте файл `.env` (или используйте существующий)

Пример `.env`:

    DB_NAME=your_db
    DB_USER=your_user
    DB_PASSWORD=your_password

    REDIS_HOST=redis
    REDIS_PORT=6379
    REDIS_PASSWORD=redis_secure_password_change_in_prod

    CACHE_TTL_DEFAULT=300
    JWT_ACCESS_EXPIRATION_MINUTES=15

3.  Запустите проект:

```{=html}
<!-- -->
```
    docker compose up --build

------------------------------------------------------------------------

### Подключение к Redis

Для проверки кеша можно подключиться к Redis через CLI:

    docker exec -it wp_labs_redis redis-cli --pass redis_secure_password_change_in_prod

------------------------------------------------------------------------

### Полезные команды Redis

Просмотр ключей:

    KEYS wp:*

Просмотр ключей по модулю:

    KEYS wp:works:*
    KEYS wp:auth:*
    KEYS wp:users:*

Получение значения:

    GET <ключ>

Проверка TTL:

    TTL <ключ>

Удаление ключа:

    DEL <ключ>

Удаление по шаблону:

    UNLINK wp:works:*

Очистка базы (для тестов):

    FLUSHDB

### Реализованный функционал

#### 1. Кеширование списка ресурсов

-   Endpoint: `GET /works`
-   Используется стратегия Cache-Aside
-   Ключ формируется с учётом пагинации:

```{=html}
<!-- -->
```
    wp:works:list:page:{page}:limit:{limit}

#### 2. Кеширование конкретного ресурса

-   Endpoint: `GET /works/<id>`
-   Ключ:

```{=html}
<!-- -->
```
    wp:works:detail:{id}

#### 3. Кеширование профиля пользователя

-   Endpoint: `GET /auth/whoami`
-   Ключ:

```{=html}
<!-- -->
```
    wp:users:profile:{userId}

#### 4. Инвалидация кеша

При изменении данных кеш автоматически очищается:

-   POST → очистка списка
-   PUT/PATCH → очистка списка + конкретного элемента
-   DELETE → очистка списка + элемента

------------------------------------------------------------------------

### Работа с access-токенами (Redis)

#### Хранение JTI

При создании access-токена его идентификатор (JTI) сохраняется в Redis:

    wp:auth:user:{userId}:access:{jti}

#### Проверка токена

При каждом защищённом запросе:

-   JWT декодируется
-   извлекается JTI
-   проверяется наличие ключа в Redis

Если ключ отсутствует → доступ запрещён (401)

#### Logout

При выходе пользователя:

-   JTI удаляется из Redis
-   кеш профиля пользователя очищается

------------------------------------------------------------------------

### Безопасность

-   Пароли не сохраняются в Redis
-   Access-токены не хранятся полностью (используется только JTI)
-   Все ключи имеют префиксы `wp:*`
-   Для всех ключей используется TTL
-   Redis защищён паролем
