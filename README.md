## Краткое описание проекта

`Web-Labs` — это backend-приложение на Django, которое разрабатывалось поэтапно в рамках девяти лабораторных работ. Каждая лабораторная работа добавляла в один общий проект новую часть функциональности: от базового клиент-серверного взаимодействия до запуска приложения в Kubernetes.

В итоговом состоянии проект поддерживает регистрацию и авторизацию пользователей, работу с профилем, CRUD-операции с произведениями, загрузку файлов в объектное хранилище, кэширование, асинхронную обработку событий, отправку приветственных писем и масштабирование API в Kubernetes.

Основные компоненты проекта:

| Компонент | Назначение |
|---|---|
| `Settings/` | настройки Django-проекта и главная маршрутизация |
| `authapp/` | регистрация, вход, JWT, OAuth и работа с токенами |
| `users/` | профиль пользователя и операции с пользователями |
| `lab2/` | REST API для работы с произведениями |
| `storage/` | загрузка, скачивание и удаление файлов |
| `common/` | общие сервисы: MongoDB, Redis, RabbitMQ, email, health endpoints |
| `k8s/` | Kubernetes-манифесты |
| `Dockerfile` | сборка Docker-образа приложения |
| `docker-compose.yml` | локальный запуск инфраструктуры |

# Лабораторная работа №2. Проектирование и реализация RESTful API

## Цель работы

Изучить архитектурный стиль REST, освоить HTTP-методы `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, реализовать CRUD API, подключить базу данных, добавить мягкое удаление, пагинацию и разделение ответственности между слоями приложения.

# Лабораторная работа №3. Авторизация и аутентификация

## Цель работы

Изучить различия между аутентификацией и авторизацией, реализовать регистрацию и вход пользователя, работу с JWT-токенами, refresh token, HttpOnly cookies, безопасное хранение паролей и защиту API-эндпоинтов.

## Ход работы

В рамках третьей лабораторной работы в проект были добавлены приложения и сервисы для работы с пользователями и авторизацией:

```text
authapp/
users/
```

Основная логика регистрации и входа находится в файлах:

```text
authapp/views.py
authapp/auth_service.py
users/mongo_service.py
```

Был реализован endpoint регистрации:

```http
POST /auth/register
```

Сценарий регистрации пользователя:

1. Клиент отправляет JSON с `email`, `password` и `phone`.
2. View создаёт DTO и передаёт данные в сервис регистрации.
3. Сервис проверяет, существует ли пользователь с таким email.
4. Пароль хэшируется.
5. Пользователь сохраняется в базе данных.
6. Создаётся событие `user.registered`.
7. Событие публикуется в RabbitMQ для дальнейшей асинхронной обработки.
8. API возвращает id и email созданного пользователя.

Пример ответа:

```json
{
  "id": "user_id",
  "email": "user@example.com"
}
```

Также были реализованы endpoints авторизации:

```http
POST /auth/login
GET  /auth/whoami
POST /auth/refresh
POST /auth/logout
POST /auth/logout-all
```

При входе пользователь отправляет `email` и `password`. Приложение ищет пользователя в базе, проверяет пароль, создаёт access token и refresh token, сохраняет данные токенов и устанавливает их в `HttpOnly` cookies.

Access token дополнительно отмечается в Redis, что позволяет проверять активность сессии и отзывать доступ до истечения срока жизни JWT. При выходе пользователя access token удаляется из Redis, а refresh token помечается как отозванный.

В модели пользователя хранятся email, телефон, хэш пароля, соль, даты создания и обновления, а также поле для мягкого удаления `deleted_at`. В проекте также предусмотрен поиск пользователя по `yandex_id`, что связано с поддержкой OAuth-авторизации.

## Заключение

В результате выполнения третьей лабораторной работы проект получил полноценную систему регистрации, входа, проверки текущего пользователя, обновления и отзыва токенов. API стало защищённым, а пользовательские пароли и токены стали храниться безопаснее.

# Лабораторная работа №5. Кеширование данных и управление сессиями с использованием Redis

## Цель работы

Изучить принципы работы Redis, реализовать кэширование часто запрашиваемых данных, настроить инвалидацию кэша, использовать Redis для управления access token и подготовить основу для distributed lock.

## Ход работы

В пятой лабораторной работе в проект был добавлен Redis. Работа с ним вынесена в общий сервис:

```text
common/cache_service.py
```

В этом сервисе реализованы методы:

```python
get()
set()
delete()
delete_by_pattern()
acquire_lock()
release_lock()
```

Redis используется в нескольких частях проекта:

- кэширование профиля пользователя;
- кэширование списка произведений;
- хранение признака активности access token;
- хранение информации об обработанных событиях;
- Redis-lock для защиты от повторной обработки событий.

При получении профиля пользователя endpoint:

```http
GET /profile
```

работает следующим образом:

1. Проверяется access token из cookies.
2. Пользователь ищется в базе данных.
3. Сначала проверяется Redis-кэш.
4. Если данные есть в кэше, они возвращаются сразу.
5. Если данных нет, профиль берётся из базы и сохраняется в Redis.

Для произведений кэш используется при получении списка:

```http
GET /works
```

После создания, изменения или удаления произведения кэш списка очищается. Это предотвращает возврат устаревших данных.

Также Redis используется для управления сессиями: при входе access token отмечается как активный, а при выходе удаляется. Это позволяет сделать logout действительно рабочим, даже если JWT ещё формально не истёк.

## Заключение

В результате выполнения пятой лабораторной работы в проект был добавлен Redis. Он ускорил получение часто используемых данных и позволил управлять пользовательскими сессиями. Также были реализованы механизмы инвалидации кэша и подготовлена основа для Redis-lock.

# Лабораторная работа №7. Хранение файлов с использованием MinIO

## Цель работы

Изучить объектные хранилища на примере MinIO, реализовать загрузку и скачивание файлов, хранение файловых метаданных в базе данных, валидацию файлов, защиту доступа и интеграцию аватара пользователя в профиль.

## Ход работы

В седьмой лабораторной работе в проект был добавлен модуль для работы с файлами:

```text
storage/
```

Для файлов были реализованы endpoints:

```http
POST   /files
GET    /files/<file_id>
DELETE /files/<file_id>
```

При загрузке файла выполняется следующий сценарий:

1. Проверяется авторизация пользователя.
2. Проверяется наличие файла в запросе.
3. Проверяется размер файла.
4. Проверяется тип файла.
5. Файл загружается в MinIO.
6. Метаданные файла сохраняются в MongoDB.
7. Пользователь получает информацию о загруженном файле.

MinIO хранит сам файл, а MongoDB хранит метаданные:

- id файла;
- оригинальное имя;
- размер;
- MIME-тип;
- bucket;
- object key;
- владелец файла.

Доступ к файлам защищён: пользователь может получить или удалить только свои файлы. Это проверяется по данным авторизации и владельцу файла в базе данных.

Модуль файлов также связан с профилем пользователя. В endpoint:

```http
POST /profile
```

можно передать `avatarFileId`. Приложение проверяет, что файл существует, принадлежит текущему пользователю и является изображением. После этого файл может использоваться как аватар профиля.

## Заключение

В результате выполнения седьмой лабораторной работы проект получил полноценную работу с файлами через MinIO. Файлы не хранятся в базе данных или файловой системе приложения: в базе сохраняются только метаданные, а сами объекты находятся в MinIO. Также была добавлена проверка доступа и возможность использовать файл как аватар пользователя.

# Лабораторная работа №8. Асинхронная обработка событий с использованием RabbitMQ

## Цель работы

Изучить брокеры сообщений и паттерн «производитель — потребитель», освоить RabbitMQ, реализовать асинхронную обработку события регистрации пользователя, отправку приветственного email, подтверждения обработки, повторные попытки и Dead Letter Queue.

## Ход работы

В восьмой лабораторной работе в проект был добавлен RabbitMQ. Логика работы с очередями находится в файле:

```text
common/rabbitmq_service.py
```

После успешной регистрации пользователя формируется событие:

```python
{
    "eventId": "...",
    "eventType": "user.registered",
    "payload": {
        "userId": "...",
        "email": "...",
        "displayName": "..."
    },
    "metadata": {
        "attempt": 1,
        "sourceService": "authapp"
    }
}
```

Это событие публикуется в RabbitMQ с routing key:

```text
user.registered
```

Consumer регистрации пользователя находится в файле:

```text
common/user_registered_consumer.py
```

Для запуска consumer-а используется Django management command:

```text
common/management/commands/consume_user_registered.py
```

Команда запуска:

```bash
python manage.py consume_user_registered
```

Сценарий обработки события:

1. Consumer подключается к RabbitMQ.
2. Слушает очередь регистрации пользователей.
3. Получает событие `user.registered`.
4. Проверяет, не было ли событие уже обработано.
5. Получает Redis-lock.
6. Отправляет приветственное письмо.
7. Помечает событие как обработанное.
8. Подтверждает сообщение через `basic_ack`.

Отправка письма реализована в файле:

```text
common/email_service.py
```

Функция:

```python
send_welcome_email()
```

Она формирует plain text и HTML-письмо и отправляет его через SMTP.

Если возникает ошибка, consumer может повторить обработку. После нескольких неудачных попыток сообщение отправляется в DLQ.

## Заключение

В результате выполнения восьмой лабораторной работы в проект была добавлена асинхронная обработка событий через RabbitMQ. Регистрация пользователя больше не зависит напрямую от отправки письма: API быстро создаёт пользователя и публикует событие, а отправка email выполняется отдельно consumer-ом.

Endpoint `/health/live` показывает, что процесс приложения жив. Endpoint `/health/ready` проверяет готовность приложения принимать трафик и доступность зависимостей:

- MongoDB;
- Redis;
- RabbitMQ;
- MinIO.

Если все зависимости доступны, возвращается `200`. Если хотя бы одна зависимость недоступна, возвращается `503`.

API запускается через Kubernetes Deployment. В нём указаны Docker-образ `wp-labs/api:1.0.0`, порт `4200`, переменные окружения из `ConfigMap` и `Secret`, а также probes:

Consumer запускается отдельным Deployment:

```text

```

Он использует тот же Docker-образ, что и API, но запускает другую команду:

```yaml
command:
  - python
  - manage.py
  - consume_user_registered
```

Для защиты от повторной обработки событий используется Redis-lock. Он работает следующим образом:

1. Формируется ключ:

```python
lock_key = f"wp:locks:events:{event_id}"
```

2. Создаётся уникальный идентификатор lock-а:

```python
lock_id = str(uuid4())
```

3. Consumer пытается получить lock через Redis-команду `SET key value NX EX`.
4. Если lock уже существует, событие обрабатывает другой consumer.
5. Если lock получен, consumer выполняет обработку события.
6. После обработки lock удаляется.

Удаление lock-а выполняется через Lua script: Redis сначала проверяет, что lock принадлежит именно этому consumer-у, и только потом удаляет его. Это защищает от случайного удаления чужой блокировки.

Масштабирование API выполняется командой:

```bash
kubectl scale deployment/api --replicas=4 -n wp-labs
```

Проверка pod-ов:

```bash
kubectl get pods -n wp-labs -l app=api
```

После масштабирования Kubernetes запускает несколько pod-ов API, а Service распределяет запросы между ними.

# Итоговое описание работы проекта

После выполнения всех девяти лабораторных работ проект `Web-Labs` представляет собой backend-приложение на Django, которое использует MongoDB для хранения данных, Redis для кэша, служебных ключей и блокировок, RabbitMQ для событий и MinIO для хранения файлов.

Полный сценарий регистрации пользователя выглядит так:

1. Клиент отправляет `POST /auth/register`.
2. API принимает JSON с email, паролем и телефоном.
3. Пароль хэшируется.
4. Пользователь сохраняется в MongoDB.
5. API публикует событие `user.registered` в RabbitMQ.
6. Consumer получает событие.
7. Consumer берёт Redis-lock.
8. Consumer отправляет приветственное письмо через SMTP.
9. Consumer помечает событие как обработанное.
10. Сообщение подтверждается в RabbitMQ.
